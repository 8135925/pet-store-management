## 1. 本期要解决的真实问题

### 1.1 临期与断货：一笔账算不清

试运行 4 个月后，老板给出三个具体数字：

1. 9 月进了 24 袋 2kg 幼犬粮，前台按货架顺序卖，压在最里面的 6 袋 11 月到期，10 月底才发现 → 直接损失 `6 × 128 = 768 元`，接近该品类月毛利的一半。
2. 同款粮 10 月分三次进货，进价分别为 78 / 82 / 85 元，系统里只有一个 `product.cost_price_cent`，月底算毛利只能拍脑袋。
3. 仓库有 38 个 SKU，每次进货后靠手写便签记「谁家、几号、多少钱」，对账要翻微信。

根因不是员工不细心，而是**现有模型把「商品」当成了「库存」**：

- `product.stock_qty` 只有一个总数，装不下「同商品不同效期、不同进价」；
- `product.expire_on` 只有一个日期（v1.0 schema 注释已预警「同商品多批次不同效期时此字段不可靠」）；
- 采购入库走的是「手工调整 +N」，没有供应商、没有进价、没有单据，事后无法追溯。

### 1.2 工资算不对，员工不信任

3 名美容师 + 1 名助理，提成规则是口头的：洗护 15%、剪毛 20%、卖卡 5%、卖粮 3 元/袋。月底老板用微信聊天记录 + 计算器算 2 小时，员工常有异议：

- 「这只猫是我洗的，单子挂在店长名下」——现有 `bill_item` 只有 `bill_id`，没有「谁做的」；
- 「这单后来反结账了，为什么还算我提成」——反结账与提成没有联动；
- 「上个月已经结过的提成，这个月又变了」——没有结算确认动作。

### 1.3 1200 个客户，只有疫苗提醒

- 客户档案攒了 1200 条，除了疫苗到期，没有任何「该联系谁」的机制；
- 洗完澡第 3 天回访「有没有挠痒」全靠美容师记性，忙起来就忘；
- 想做一次老客召回，只能把客户列表导出来一条条看「上次来是什么时候」；
- 凶猛犬、怕吹风机、皮肤敏感这些信息写在 `pet.habit` 自由文本里，新员工根本不会去看。

### 1.4 前台每天重复的十分钟

- 客户问「卡里还剩几次」，前台要开电脑查，再手打一段微信发过去；
- 结账后要按 Ctrl+P，页眉页脚、侧边栏全打出来，58mm 小票机上排版错乱；
- 寄养客户来接狗，要口头报「住了 5 晚、洗澡 1 次、加罐头 2 个」，没有一张能给客户带走的单子。

### 1.5 出了事查不清

- 9 月有一单被反结账，库存回补了，但没人记得是谁、为什么；
- 老板想验证「库存结存 = 流水求和」，只能让开发连数据库跑 SQL；
- 备份文件有一堆，真出事时不知道哪个能用、怎么恢复。

## 2. 范围界定

### 2.1 本期做（P2）

| 模块 | 一句话 | 需求数 | 主要交付 |
|---|---|---|---|
| M11 采购与批次库存 | 从「手工加库存」升级为「采购单 → 批次 → 先进先出」 | 12 | 供应商、采购入库、批次效期、FEFO 出库、盘点、报损 |
| M12 员工与提成 | 每笔收入能追溯到人，提成一次算对 | 8 | 员工档案、明细归属、提成规则、提成记录、月度结算 |
| M13 客户经营 | 把 1200 条档案变成「今天该联系谁」 | 7 | 宠物/客户标签、回访任务、待办中心、触达记录、召回清单 |
| M14 小票打印 | 前台不用再手打微信 | 4 | 58mm 小票、售卡小票、寄养单、补打 |
| M15 经营报表 | 从「记了多少」到「赚了多少、该补什么」 | 5 | 动销/滞销、补货建议、批次毛利、经营月报、CSV 导出 |
| M16 运维与数据安全 | 出事能查、能恢复 | 3 | 审计日志、数据体检、备份恢复 |

合计 **39 条需求**（M11 12 + M12 8 + M13 7 + M14 4 + M15 5 + M16 3）。

### 2.2 本期不做（明确排除）

| 项 | 为什么不做 | 归入 |
|---|---|---|
| 储值余额、预付卡资金池 | 涉预付资金合规与余额审计，单店版不碰 | P3（需合规评估） |
| 会员等级、积分、优惠券 | 宠物店缺的是「记得住客户」，不是促销工具 | P3 |
| 多门店、多仓、调拨 | 单店单仓；数据结构留了 `store_id` 扩展位但不实现 | P3 |
| 微信/短信自动发送 | 需第三方通道资质与模板报备；本期只做「话术生成 + 一键复制 + 触达留痕」 | P3 |
| 支付通道、退款 | 产品红线：只记账，不接通道；只做当日整单反结账 | 永不 |
| 医疗病历、处方、住院 | 非医院业态（v1.0 待确认 #1 默认社区店） | 不做 |
| 财务总账、供应商应付账款 | 属会计软件范畴；本期只记「进了多少货、花了多少钱」 | 不做 |
| 员工排班、考勤、工资发放 | 提成算清即止，工资由老板线下发 | 不做 |
| ESC/POS 指令直连打印机 | 浏览器打印已满足 58mm 需求，驱动差异反而增加交付成本 | 不做 |
| 快递代发、线上商城 | 与门店台账无关 | 不做 |

### 2.3 与 P3 的分界

本期结束时，系统应能回答：**「这个月赚了多少、钱被哪些货压住了、谁该发多少提成、今天该联系哪些客户」**。
P3 再回答：**「我能不能开第二家店、能不能做预付卡」**——那是另一套资金与多租户模型，不在本期数据结构里提前埋雷。

## 3. 业务规则（新增，延续 BR-01~BR-14）

| 编号 | 规则 | 违反后果 |
|---|---|---|
| **BR-15** | **批次优先出库（FEFO）**：销售出库按 `expire_on` 升序、`received_at` 升序、`id` 升序选批次；**已过期批次不参与自动出库**，只能走报损 | 先卖新货、旧货压到过期 = 每月白扔几百元 |
| **BR-16** | **批次余额是余额表**：`product_batch.qty_left` 允许 UPDATE（与 `product.stock_qty` 同性质），但每次变动必须同时写 `product_ledger`，且 `qty_left` 之和必须等于 `product.stock_qty` | 批次与总库存对不上，盘点永远平不了 |
| **BR-17** | **盘点只走单据**：任何库存修正必须由盘点单（`stock_take`）确认后产生 `ADJUST` 台账，禁止提供「直接改库存」入口 | 无凭证改数 = 盘点失去意义，也查不出谁改的 |
| **BR-18** | **盘点确认不可逆**：确认后单据为终态，若盘错只能再盘一次（生成新的调整台账），不允许修改历史盘点单 | 改历史 = 账无法自证 |
| **BR-19** | **提成基数 = 明细折后金额**：`bill_item.amount_cent`；次卡抵扣行（`paid_by_card=1`）基数记 0、不计提成（钱在售卡当天已收）；售卡提成按 `bill.received_cent` | 卡抵扣再提成 = 一件服务发两次钱 |
| **BR-20** | **提成比例用万分比整数**：`ratio_bp`，如 1500 = 15%；`amount = round(base × ratio_bp / 10000) + fixed_cent`，全库无浮点 | 浮点累计误差导致工资差几毛，员工一定发现 |
| **BR-21** | **反结账必须冲销提成**：生成一条负数 `commission_record`，**不删除**原记录；已结算月份的提成不允许变更（系统只允许当日反结账，天然规避） | 单子退了、提成还在 = 老板白付钱 |
| **BR-22** | **提成结算需确认**：`DRAFT → CONFIRMED`，确认时把当月未结算记录打上 `settle_id`；确认后不可撤销 | 员工对完账又变数 = 信任崩塌 |
| **BR-23** | **触达必须留痕**：任何电话/微信/到店沟通记录渠道、结果、操作人、时间；同一任务 3 天内不重复进入「今日待办」 | 三个员工轮流打同一个电话，客户反感 |
| **BR-24** | **小票只做展示，不做二次计算**：金额、余额、晚数全部取单据快照字段，禁止在小票页重新算 | 小票与系统不一致 = 纠纷证据失效 |
| **BR-25** | **备份恢复必须停机**：Web 端只做「校验 + 准备 + 写标记」，实际替换由启动脚本完成；恢复前自动备份当前库，操作必须二次确认并进审计 | 恢复一半断电 = 数据全毁 |

## 4. 数据库设计

全部新表使用 `CREATE TABLE IF NOT EXISTS` 追加到 `schema.sql` 末尾；存量表变更由 `DataInitializer` 幂等迁移（本期新增 `schema_version` 表记录已执行版本，替代逐列 `PRAGMA` 探测）。

### 4.1 supplier 供应商

```sql
CREATE TABLE IF NOT EXISTS supplier (
  id         INTEGER PRIMARY KEY AUTOINCREMENT,
  name       TEXT    NOT NULL,                -- 供应商名称，如「XX 宠物食品批发」
  contact    TEXT,                            -- 联系人
  phone      TEXT,                            -- 电话，断货时直接打
  address    TEXT,
  main_category TEXT,                         -- 主营：主粮/零食/用品/保健（展示用）
  remark     TEXT,
  is_active  INTEGER NOT NULL DEFAULT 1,      -- 停用不删，历史采购单仍可追溯
  created_at TEXT    NOT NULL
);
CREATE UNIQUE INDEX IF NOT EXISTS uk_supplier_name ON supplier(name);
```

### 4.2 purchase_order / purchase_item 采购入库单

```sql
CREATE TABLE IF NOT EXISTS purchase_order (
  id             INTEGER PRIMARY KEY AUTOINCREMENT,
  order_no       TEXT    NOT NULL,            -- P + yyyyMMdd + 4 位序号，如 P202610260001
  supplier_id    INTEGER NOT NULL REFERENCES supplier(id),
  status         TEXT    NOT NULL DEFAULT 'DRAFT',
                 -- DRAFT 草稿可改 / RECEIVED 已入库（终态）/ CANCELLED 已作废（仅草稿可作废）
  total_cost_cent INTEGER NOT NULL DEFAULT 0, -- 本单进货金额合计（分）
  item_count     INTEGER NOT NULL DEFAULT 0,  -- 商品行数，列表展示用
  received_at    TEXT,                        -- 确认入库时间
  operator       TEXT,                        -- 确认入库人
  remark         TEXT,
  created_at     TEXT    NOT NULL,
  created_by     TEXT
);
CREATE UNIQUE INDEX IF NOT EXISTS uk_purchase_no ON purchase_order(order_no);
CREATE INDEX IF NOT EXISTS idx_purchase_supplier ON purchase_order(supplier_id, created_at);
CREATE INDEX IF NOT EXISTS idx_purchase_status ON purchase_order(status, created_at);

CREATE TABLE IF NOT EXISTS purchase_item (
  id             INTEGER PRIMARY KEY AUTOINCREMENT,
  purchase_id    INTEGER NOT NULL REFERENCES purchase_order(id),
  product_id     INTEGER NOT NULL REFERENCES product(id),
  qty            INTEGER NOT NULL,            -- 进货数量，> 0
  unit_cost_cent INTEGER NOT NULL,            -- 本次进价（分），与商品参考成本价独立
  amount_cent    INTEGER NOT NULL,            -- qty × unit_cost_cent
  batch_no       TEXT,                        -- 供应商批号/生产批号，可空
  expire_on      TEXT,                        -- 有效期至 'yyyy-MM-dd'；不管理效期可空
  remark         TEXT
);
CREATE INDEX IF NOT EXISTS idx_purchase_item_pid ON purchase_item(purchase_id);
```

### 4.3 product_batch 批次（本期核心）

```sql
CREATE TABLE IF NOT EXISTS product_batch (
  id               INTEGER PRIMARY KEY AUTOINCREMENT,
  product_id       INTEGER NOT NULL REFERENCES product(id),
  purchase_item_id INTEGER,                   -- 来源采购明细；期初/盘盈批次为 NULL
  batch_no         TEXT,                      -- 供应商批号，仅展示
  expire_on        TEXT,                      -- 有效期至；NULL = 该批次不管理效期
  qty_in           INTEGER NOT NULL,          -- 入库数量（写入后不变）
  qty_left         INTEGER NOT NULL,          -- 当前剩余（余额表，允许 UPDATE，见 BR-16）
  unit_cost_cent   INTEGER NOT NULL DEFAULT 0,-- 本批次成本单价（毛利按此算，不再看商品档案）
  source           TEXT    NOT NULL DEFAULT 'PURCHASE',
                   -- PURCHASE 采购入库 / OPENING 期初库存 / STOCK_TAKE 盘盈 / RETURN 退货入库
  status           TEXT    NOT NULL DEFAULT 'NORMAL',
                   -- NORMAL 可用 / EXHAUSTED 已售罄 / EXPIRED 已过期 / VOID 已作废（报损/冲销）
  received_at      TEXT    NOT NULL,          -- 入库时间，FEFO 次序依据之一
  created_at       TEXT    NOT NULL,
  CHECK (qty_left >= 0 AND (qty_left <= qty_in OR source = 'STOCK_TAKE'))
);
CREATE INDEX IF NOT EXISTS idx_batch_fefo ON product_batch(product_id, status, expire_on, received_at);
CREATE INDEX IF NOT EXISTS idx_batch_expire ON product_batch(expire_on, status); -- 临期看板
```

说明：`source='STOCK_TAKE'`（盘盈）允许 `qty_left = qty_in` 且 `qty_in` 即盘盈数量，`CHECK` 的第二个分支为此保留；其余来源严格 `qty_left ≤ qty_in`。

### 4.4 stock_take / stock_take_item 盘点单

```sql
CREATE TABLE IF NOT EXISTS stock_take (
  id           INTEGER PRIMARY KEY AUTOINCREMENT,
  take_no      TEXT    NOT NULL,              -- T + yyyyMMdd + 4 位序号
  scope        TEXT    NOT NULL DEFAULT 'ALL',-- ALL 全盘 / CATEGORY 按分类 / SELECTED 指定商品
  scope_value  TEXT,                          -- 分类编码或商品 id 列表（逗号分隔）
  status       TEXT    NOT NULL DEFAULT 'COUNTING',
               -- COUNTING 盘点中 / CONFIRMED 已确认（终态）/ CANCELLED 已作废
  item_count   INTEGER NOT NULL DEFAULT 0,
  diff_count   INTEGER NOT NULL DEFAULT 0,    -- 有差异的商品数
  diff_amount_cent INTEGER NOT NULL DEFAULT 0,-- 差异金额（盘亏为负）
  started_at   TEXT    NOT NULL,
  confirmed_at TEXT,
  operator     TEXT,
  remark       TEXT,
  created_at   TEXT    NOT NULL
);
CREATE UNIQUE INDEX IF NOT EXISTS uk_take_no ON stock_take(take_no);
CREATE INDEX IF NOT EXISTS idx_take_status ON stock_take(status, started_at);

CREATE TABLE IF NOT EXISTS stock_take_item (
  id           INTEGER PRIMARY KEY AUTOINCREMENT,
  take_id      INTEGER NOT NULL REFERENCES stock_take(id),
  product_id   INTEGER NOT NULL REFERENCES product(id),
  system_qty   INTEGER NOT NULL,              -- 建单时快照：SUM(qty_left)
  counted_qty  INTEGER,                       -- 实盘数；NULL = 未盘
  diff_qty     INTEGER,                       -- 确认时落库 = counted - system
  cost_cent    INTEGER NOT NULL DEFAULT 0,    -- 差异金额用的成本单价（商品参考成本）
  reason       TEXT,                          -- 差异原因：破损/过期/录错/丢失/其他
  remark       TEXT
);
CREATE UNIQUE INDEX IF NOT EXISTS uk_take_item ON stock_take_item(take_id, product_id);
```

### 4.5 员工与提成

```sql
CREATE TABLE IF NOT EXISTS staff (
  id         INTEGER PRIMARY KEY AUTOINCREMENT,
  name       TEXT    NOT NULL,                -- 员工姓名（会印在小票「服务人员」上）
  role       TEXT    NOT NULL DEFAULT 'GROOMER',
             -- GROOMER 美容师 / ASSISTANT 助理 / CASHIER 前台 / MANAGER 店长
  phone      TEXT,
  hire_on    TEXT,                            -- 入职日期
  leave_on   TEXT,                            -- 离职日期；有历史单据只停用不删除
  is_active  INTEGER NOT NULL DEFAULT 1,
  created_at TEXT    NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_staff_active ON staff(is_active, role);

CREATE TABLE IF NOT EXISTS commission_rule (
  id             INTEGER PRIMARY KEY AUTOINCREMENT,
  scope          TEXT    NOT NULL,            -- SERVICE / PRODUCT / BOARDING / CARD / ALL
  ref_id         INTEGER,                     -- SERVICE→service_item.id；PRODUCT→product.id；其余 NULL
  staff_role     TEXT,                        -- 限定岗位；NULL = 不限
  ratio_bp       INTEGER NOT NULL DEFAULT 0,  -- 万分比提成，1500 = 15%
  fixed_cent     INTEGER NOT NULL DEFAULT 0,  -- 固定提成（分/件 或 分/单）
  effective_from TEXT    NOT NULL,            -- 'yyyy-MM-dd'
  effective_to   TEXT,                        -- NULL = 长期有效
  is_active      INTEGER NOT NULL DEFAULT 1,
  remark         TEXT,
  created_at     TEXT    NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_rule_scope ON commission_rule(scope, ref_id, is_active);

CREATE TABLE IF NOT EXISTS commission_record (
  id             INTEGER PRIMARY KEY AUTOINCREMENT,
  staff_id       INTEGER NOT NULL REFERENCES staff(id),
  bill_id        INTEGER NOT NULL,            -- 不设外键，与 card_consume_log 同理由
  bill_item_id   INTEGER,                     -- 售卡提成为 NULL
  biz_type       TEXT    NOT NULL,            -- SERVICE / PRODUCT / BOARDING / CARD
  base_cent      INTEGER NOT NULL,            -- 提成基数（折后金额）
  ratio_bp       INTEGER NOT NULL DEFAULT 0,
  fixed_cent     INTEGER NOT NULL DEFAULT 0,
  amount_cent    INTEGER NOT NULL,            -- 可为负（反结账冲销）
  business_date  TEXT    NOT NULL,
  settle_id      INTEGER,                     -- 所属结算单；NULL = 未结算
  reverse_of_id  INTEGER,                     -- 冲销行指向被冲销记录 id；正常记录为 NULL
  remark         TEXT,
  created_at     TEXT    NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_comm_staff_date ON commission_record(staff_id, business_date);
CREATE INDEX IF NOT EXISTS idx_comm_settle ON commission_record(settle_id);
-- 同一明细只允许一条正向记录 + 一条冲销记录（冲销行以 reverse_of_id 参与唯一键）
CREATE UNIQUE INDEX IF NOT EXISTS uk_comm_item
  ON commission_record(bill_item_id, staff_id, biz_type, IFNULL(reverse_of_id, 0))
  WHERE bill_item_id IS NOT NULL;
CREATE UNIQUE INDEX IF NOT EXISTS uk_comm_bill_card
  ON commission_record(bill_id, staff_id, biz_type, IFNULL(reverse_of_id, 0))
  WHERE biz_type = 'CARD';

CREATE TABLE IF NOT EXISTS commission_settle (
  id           INTEGER PRIMARY KEY AUTOINCREMENT,
  settle_no    TEXT    NOT NULL,              -- M + yyyyMM + 4 位序号
  month        TEXT    NOT NULL,              -- 'yyyy-MM'
  staff_id     INTEGER NOT NULL REFERENCES staff(id),
  total_cent   INTEGER NOT NULL DEFAULT 0,
  record_count INTEGER NOT NULL DEFAULT 0,
  status       TEXT    NOT NULL DEFAULT 'DRAFT', -- DRAFT / CONFIRMED
  confirmed_at TEXT,
  operator     TEXT,
  remark       TEXT,
  created_at   TEXT    NOT NULL
);
CREATE UNIQUE INDEX IF NOT EXISTS uk_settle_staff_month ON commission_settle(staff_id, month);
```

提成规则匹配优先级（结账时执行）：
`ref_id 精确匹配 > scope='ALL'`；同优先级取 `effective_from` 最新一条；`staff_role` 不匹配则跳过。无规则 → 不生成记录，不报错。

### 4.6 客户经营

### 4.9 期初批次初始化（上线必做，一次性）

历史数据只有 `product.stock_qty`，没有批次。上线当天必须执行一次「期初批次初始化」：

- 对每个 `stock_qty > 0` 且尚无批次的商品，生成一条批次：
  `source='OPENING'`，`qty_in = qty_left = product.stock_qty`，`unit_cost_cent = product.cost_price_cent`，`expire_on = product.expire_on`，`received_at = 当前时间`；
- 幂等：已存在 `source='OPENING'` 批次的商品跳过；
- 入口：`/system/migration`（ADMIN），执行前强制提示「请先完成一次实物盘点」并记录审计；
- 未初始化的商品在批次模式下禁止销售（提示「该商品未初始化批次，请先入库或初始化」），防止出现「有库存但无法出库」。

| 表 | 年增量（单店） | 说明 |
|---|---|---|

## 7. 关键流程详设

### 7.1 F10 采购入库（事务）

```
输入：purchaseId（DRAFT）
事务开始
  1. 校验 status='DRAFT'，明细非空，供应商 is_active=1
  2. 逐行校验：qty>0、unit_cost>=0、amount=qty*unit_cost
  3. 逐行 INSERT product_batch：
       qty_in = qty_left = qty
       unit_cost_cent = 行进价
       expire_on = 行效期（为空且商品有 shelf_life_days 则按 received_at 推算）
       source='PURCHASE'，status='NORMAL'，received_at=now
  4. 逐行 UPDATE product SET stock_qty = stock_qty + qty
  5. 逐行 INSERT product_ledger(
       biz_type='PURCHASE', qty_change=+qty,
       before_qty = 更新前库存, after_qty = before+qty,
       unit_cost_cent = 行进价, batch_id = 新批次id,
       ref_type='PURCHASE', ref_id=purchaseId, operator)
  6. UPDATE purchase_order SET status='RECEIVED', received_at=now, operator=?
事务提交
```

台账的 `before/after` 必须按行连续递推（同一商品多行时，后一行的 before = 前一行的 after），保证求和等于结存。

### 7.2 F11 FEFO 出库（事务，嵌在结账内）

```
输入：productId, qty, billId, operator
  1. UPDATE product SET stock_qty = stock_qty - #{qty}
     WHERE id=? AND stock_qty >= #{qty}
     影响 0 行 → STOCK_NOT_ENOUGH（整单回滚）
  2. before = 扣减前库存；after = before - qty
  3. 取可用批次：
     SELECT * FROM product_batch
     WHERE product_id=? AND status='NORMAL' AND qty_left>0
       AND (expire_on IS NULL OR expire_on >= #{today})
     ORDER BY (expire_on IS NULL) ASC, expire_on ASC, received_at ASC, id ASC
  4. remaining = qty；takenSoFar = 0
     for batch in batches:
        take = min(remaining, batch.qty_left)
        UPDATE product_batch
           SET qty_left = qty_left - take,
               status = CASE WHEN qty_left - take = 0 THEN 'EXHAUSTED' ELSE status END
         WHERE id=? AND qty_left >= take
        ledgerBefore = before - takenSoFar
        INSERT product_ledger(biz_type='SALE', qty_change=-take,
             before_qty=ledgerBefore, after_qty=ledgerBefore-take,
             unit_cost_cent=batch.unit_cost_cent, batch_id=batch.id,
             ref_type='BILL', ref_id=billId)
        remaining -= take; takenSoFar += take
        if remaining == 0: break
  5. remaining > 0 → STOCK_NOT_ENOUGH（批次与总库存不一致，整单回滚）
  6. bill_item.batch_id = 仅当 takenSoFar 来自单一批次时填该批次 id，否则 NULL
```

**兼容开关**：`store_config.inventory_batch_enabled=0` 时退化为 v1.1 逻辑（整店库存 + 商品参考成本），用于上线异常时应急回退；报表口径不受影响（仍按台账聚合）。

### 7.3 F12 盘点确认（事务）

```
输入：takeId
事务开始
  1. 校验 status='COUNTING'
  2. 逐行遍历 stock_take_item：
     counted_qty 为 NULL → 跳过（视为未盘，不调整）
     diff = counted - system
     diff == 0 → 跳过
     盘亏（diff < 0）：
        按 FEFO 扣批次（同 F11），qty_change = diff，biz_type='TAKE'
        写台账 remark='盘点 {take_no} 盘亏：{reason}'
     盘盈（diff > 0）：
        INSERT product_batch(source='STOCK_TAKE', qty_in=qty_left=diff,
             unit_cost_cent=商品参考成本, expire_on=NULL, received_at=now)
        写台账 biz_type='TAKE'，qty_change=+diff，batch_id=新批次
  3. UPDATE product.stock_qty = 扣减/增加后的真实值（逐行）
  4. UPDATE stock_take SET status='CONFIRMED', confirmed_at, diff_count, diff_amount_cent
  5. 写 audit_log(action='STOCK_TAKE_CONFIRM')
事务提交
```

盘点差异金额 = `Σ(diff × 商品参考成本)`，仅用于管理参考，不生成会计凭证。

**盘点期间发生销售的处理**：`system_qty` 是建单快照，确认时若该商品当前批次合计已小于快照（说明盘点期间卖出过），页面提示「盘点期间有 N 笔销售，差异可能包含正常销售」，由店长选择「重新盘点」或「继续确认」。继续确认时按快照差异调整，调整后台账与结存仍保持一致（差异计入盘点单，不影响已发生的销售台账）。

### 7.4 F13 提成计算与结算

**结账时（`BillService.settle` 事务内）**：

```
for item in bill_items:
    if item.paid_by_card == 1: continue                  // BR-19
    staffId = item.staff_id ?: 当前账号关联员工
    if staffId == null: continue                          // 未指定则不计提成
    rule = matchRule(scope=item.item_type, refId=item.ref_id, staffRole)
    if rule == null: continue
    base = item.amount_cent
    amount = round(base * rule.ratio_bp / 10000) + rule.fixed_cent
    if amount == 0: continue
    INSERT commission_record(...)

售卡单（bill_type='CARD'）：
    base = bill.received_cent
    rule = matchRule(scope='CARD')
    INSERT 一条记录（bill_item_id=NULL）
```

**反结账时**：

```
按 bill_id 查 amount_cent > 0 的 commission_record
for r in records:
    INSERT commission_record(staff_id=r.staff, bill_id=r.bill,
        bill_item_id=r.bill_item_id, biz_type=r.biz_type,
        base_cent=-r.base_cent, ratio_bp=r.ratio_bp, fixed_cent=0,
        amount_cent=-r.amount_cent, business_date=当日营业日,
        reverse_of_id=r.id, remark='反结账冲销 '+bill_no)
```

冲销行通过 `reverse_of_id` 指向原记录，唯一索引 `(bill_item_id, staff_id, biz_type, IFNULL(reverse_of_id,0))` 保证「一个明细最多一条正向 + 一条冲销」；重复反结账在单据状态条件更新处已被拦截，不会产生第二条冲销。

**月度结算**：

```
生成：SELECT staff_id, COUNT(*), SUM(amount_cent)
      FROM commission_record
      WHERE settle_id IS NULL AND business_date BETWEEN 月初 AND 月末
      GROUP BY staff_id
      → INSERT commission_settle(status='DRAFT')
确认：校验 DRAFT → UPDATE commission_record SET settle_id=? WHERE 同条件
      → UPDATE commission_settle SET status='CONFIRMED'
```

### 7.5 F14 回访任务生成（每日 04:10 定时任务）

```
1) 服务回访：查 business_date = 今日-3 且 status='SETTLED' 的 SALE 单
   按 (customer_id, pet_id) 去重，插入 type='SERVICE_FOLLOW_UP', due_on=今日
2) 宠物生日：pet.birthday 的月日 = 今日+7 的月日（处理 2/29 → 2/28）
   插入 type='BIRTHDAY', due_on=今日+7

```

`uk_follow_up` 保证重复执行不会产生重复任务（每天可安全重跑）。

### 7.7 F16 备份恢复

```
Web 端（ADMIN）：
  1. 选择已有备份 或 上传 .db 文件
  2. 服务端校验：PRAGMA integrity_check == 'ok'
                  必需表存在（bill/customer/product/sys_user）
                  sys_user 至少 1 个 ACTIVE 管理员
  3. 自动备份当前库（VACUUM INTO data/backup/pre-restore-{ts}.db）
  4. 写 data/restore.pending（JSON：文件路径、操作人、时间）
  5. 打开维护模式（内存标志），所有请求返回维护页
  6. 页面提示「已准备就绪，请关闭服务并重新执行 start.bat」

  1. 若存在 data/restore.pending：
```

## 9. 报表口径（新增指标定义）

| 指标 | 定义 | 口径要点 |
|---|---|---|
| 商品成本 | `SUM(product_ledger.unit_cost_cent × -qty_change)`，`biz_type='SALE'` | 按批次成本，不再取商品档案成本价；历史单成本为 0，页面注明 |
| 毛利 | 商品收入 − 商品成本 | 服务/寄养毛利暂不计算（人力成本不在系统内） |
| 动销率 | 期间销量 ÷（期初库存 + 期间入库） | 期间入库取 `PURCHASE` 台账求和 |
| 周转天数 | 平均库存 ÷ 日均销量 | 平均库存 =（期初 + 期末）/ 2；无销量返回「—」 |
| 建议进货量 | 日均销量 × 补货周期 − 现有库存 | 结果 < 0 取 0；补货周期可配（默认 7 天） |
| 客单价 | 期间实收 ÷ 期间有效消费客户数 | 同一客户一天多单算一次 |
| 复购率 | 期间消费 ≥ 2 次客户 ÷ 期间消费客户 | 按 `business_date` 去重 |
| 流失客户 | 最后消费日距今天 > `recall_days` 且累计消费 > 0 | 阈值可配，默认 90 天 |
| 员工业绩 | 该员工明细的 `amount_cent` 合计（排除卡抵扣行） | 反结账单不计入 |
| 提成金额 | `SUM(commission_record.amount_cent)`，含负数冲销 | 已结算/未结算分列展示 |

## 10. 边界与异常场景（24 条，开发自测用）

| # | 场景 | 系统行为 |
|---|---|---|
| 1 | 采购单只有 1 行且数量为 0 | 拒绝确认入库，提示「明细数量必须大于 0」 |
| 2 | 确认入库时网络中断 | 事务回滚，单据仍为 DRAFT，可重试 |
| 3 | 同一商品同一次采购两行、效期不同 | 生成两个批次，两个批次独立 FEFO |
| 4 | 商品不管理效期（`expire_on` 为空） | 批次 `expire_on` 为 NULL，排序时排在有有效期批次之后，按入库时间先进先出 |
| 5 | 销售 10 件，最早批次只剩 3 件 | 拆 3 + 7 两条台账，成本分别取各自批次 |
| 6 | 批次库存够、总库存不够 | 以总库存条件更新为准，拒绝并回滚 |
| 7 | 总库存够、批次库存不够（数据不一致） | 拒绝 `STOCK_NOT_ENOUGH`，提示先做数据体检/盘点 |
| 8 | 商品已过期批次仍在库 | 不参与自动出库；临期看板标红；报损后才能清账 |
| 9 | 报损 5 件，批次剩 8 件 | 批次剩余 3，写 `VOID` 台账，必须填原因 |
| 10 | 盘点中途有销售发生 | 以建单时 `system_qty` 快照为准，差异按快照计算；确认页提示「盘点期间有 N 笔销售」 |
| 11 | 盘点未录任何数量就确认 | 拒绝，提示「至少录入一个实盘数」 |
| 12 | 同一商品存在未确认盘点单，再建盘点 | 拒绝，提示先确认或作废 |
| 13 | 盘盈商品无参考成本 | 以 0 成本建批次，页面提示补录成本 |
| 14 | 提成规则同 scope 两条都生效 | 取 `effective_from` 最新一条，页面提示存在重叠 |
| 15 | 员工离职后其历史提成 | 保留可查；不再生成新记录；结算仍可做 |
| 16 | 当天结账后反结账，再重新结账 | 提成先冲销再重算，最终金额与重结一致 |
| 17 | 售卡单反结账 | 本期不支持售卡反结账（沿用 v1.1 限制），提示「售卡收款单不支持反结账」 |
| 18 | 提成结算后再反结账上月单 | 系统限制只能反结账当日单，不会发生；如手工改库，体检项 6 会报异常 |
| 19 | 同一客户同一天两条服务回访任务 | 唯一索引拦截，只保留一条 |
| 20 | 客户明确拒绝回访 | 任务标 SKIPPED，30 天内不再自动生成同类任务 |
| 21 | 58mm 小票内容超过一页 | 自动分页，页脚金额只在最后一页出现 |
| 22 | 恢复的备份文件损坏 | 校验失败即拒绝，不写标记，当前库不受影响 |
| 23 | 恢复准备就绪后未重启就继续开单 | 维护模式拦截所有写操作，只允许查看 |
| 24 | 关闭批次模式后再打开 | 期间产生的销售台账无 `batch_id`，批次余额与总库存可能不一致，需盘点一次 |

## 12. 验收清单（32 条，逐条点过才算交付）

**采购与批次**
1. 建供应商 2 家，同名被拒；停用后不出现在新采购单下拉。
2. 新建采购单 3 行（同商品两行不同效期），草稿可改可删行。
3. 确认入库后：批次列表出现 3 条（其中同商品 2 条），商品库存增加正确。
4. 采购入库台账 `before/after` 连续，求和等于当前库存。
5. 已入库单据不可再编辑，重复点「确认入库」被拒。
6. 销售 10 件、最早批次剩 3 件：生成 2 条台账，成本分别取 3 件与 7 件所属批次。
7. 已过期批次不出现在自动出库范围；报损 5 件后批次剩余正确。
8. 批次剩余合计 = `product.stock_qty`（数据体检无异常）。
9. 全盘 20 个 SKU，盘亏 2 个、盘盈 1 个，确认后库存与台账一致，差异金额正确。
10. 盘点未录任何数量时确认被拒；同一商品存在未确认盘点单时不能重复建单。
11. 盘点确认后单据不可修改；数据体检 6 项均无异常。

**员工与提成**

32. 反结账、盘点确认等操作在审计日志可查（人/时间/对象）；恢复备份需二次确认，未重启前处于维护模式，重启后自动完成替换且可正常登录。

## 14. 非功能需求（延续 v1.0/v1.1，增量部分）

| 项 | 要求 |
|---|---|
| 性能 | 批次 FEFO 查询 < 10ms（索引命中）；盘点录入 500 SKU 页面操作无卡顿（每行独立提交或整页一次性提交均可，需实测）；CSV 导出 1 万行 < 5s |
| 内存 | CSV 导出必须流式写 `HttpServletResponse`，禁止先查全量到 `List` |
| 事务 | F10/F11/F12/F13 与结账同规范：`@Transactional(rollbackFor = Exception.class)`；提成与结账同事务，要么都成功要么都回滚 |
| 并发 | 采购确认、盘点确认、提成结算均使用状态条件更新（`WHERE status=...`），重复提交影响 0 行即报错 |
| 兼容 | 全部新表 `IF NOT EXISTS`；存量表按 `schema_version` 幂等迁移；关闭批次模式可退回 v1.1 逻辑 |
| 数据安全 | 恢复备份必须二次确认 + 自动备份当前库 + 审计；审计日志不含密码、不含完整手机号（中间 4 位掩码） |
| 打印 | 58mm 首屏渲染 < 1s；页面不加载侧边栏与图表脚本；支持 80mm 通过 `receipt_width` 切换样式 |
| 打包 | `thymeleaf.cache: true`；单 fat jar；交付件结构与 v1.1 一致 |
